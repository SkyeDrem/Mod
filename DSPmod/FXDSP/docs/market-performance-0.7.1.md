# 现有行情模型与规模评估（2026-10-25）

本次只调整持仓面板，没有更改行情算法或性能实现。

## 当前涨跌规则

报价由 `Core/SpotMarket.cs` 推进，保证金市场设置为每 90 tick（1.5 游戏秒）产生一次新价。每个品种使用独立的 Xorshift32 状态。

令 `u` 为 [-1,1] 的伪随机噪声，`p` 为当前价格，`m` 为趋势动量：

```text
m_next = 0.88 * m + 0.0024 * u
p_next = p + 0.006 * (1 - p) + p * (m_next + 0.008 * u)
p_next = round(clamp(p_next, 0.2, 5.0), 8)
```

- `0.88*m` 让已有趋势逐渐衰减而非立即消失。
- `0.006*(1-p)` 把价格缓慢拉向基准 1。
- 噪声提供新的涨跌扰动；同一噪声同时进入动量和当期波动。
- 所有品种目前使用相同参数，只有种子不同。种子按品种固定，新账户的随机序列可重复；存档保留 RNG 和动量，读档继续原序列。
- 玩家买卖不改变报价，不读取工厂产量、库存、消费、物流或供需；没有跨品种联动或事件驱动。
- K 线实体连接真实前后报价，上下影线采用独立确定性随机装饰，不影响成交或爆仓。

因此它是带动量、均值回归和边界的随机过程，不是无记忆的纯随机行走，也不是供需撮合市场。

## 本机压力测量

测试在独立 .NET 10.0.13 进程运行，关闭 TieredCompilation，复用未修改的 Core 源码。不是 Unity/Mono 游戏内实测，不包含原版工厂模拟、Unity UI、输入、物品原型查询、真实持仓列表渲染或磁盘写入；不能据此承诺 FPS。

每种规模 3 次、每次 600 模拟帧，60 tick/s；每个账户预留 120 条历史，所有报价同步发生。主要组为空仓，另测 100 个市场有 10/100 项 1×多仓的情况。市场数量超过当前目录的组是模拟扩展，不代表现产品已支持这些目录项。

测量复现 `MarketSession.Tick` 的全账户推进/历史读取，以及 `PreserveForReload` 每 30 tick 的两次完整序列化。缓存保留为内存字节数组，无真实游戏、Profile、旁档写入。

## 扩展判断

- 当前 9 市场基础成本很小。100～200 市场在数据计算上可行，但报价和缓存重合时会出现一次批量工作，满载工厂或 Unity Mono 环境下仍需实测。
- 推进价格是 O(N)，目前每次更新还会重建各账户最多 120 个包装历史点；这部分额外分配比伪随机数本身更值得优化。
- 缓存每半游戏秒完整序列化两遍。100/200 市场仅缓存就约分配 5.2/10.4 MiB 每游戏秒，可能增加 Unity GC 压力。
- 当前读取旁档上限为 1 MiB；500 市场且历史满时已经超出。扩展到数百全物品市场前必须同步规划保存上限与迁移，不能只加目录。
- UI 只绘制当前品种的最近 60 根 K 线，未来应继续这样做，不同时构建全部品种的图表。全资源品种选择需分页或滚动。

建议扩展前先减少重复全量序列化和历史点分配，再错开不同品种的报价批次，最后在真实工厂存档中测主线程耗时与 GC。关键账户操作与 F6 状态交接必须继续即时保存，不能为了省开销丢失资产。

本机复现程序与完整数据位于忽略目录 `artifacts/performance-0.7.1`，用项目本地 SDK 运行，设置 `DOTNET_TieredCompilation=0`。
